# プロジェクト憲章（Constitution）

## 1. 目的と成功条件
- 目的：ユーザーが迷わず使える、保守しやすいプロダクトを素早く改善できる状態を作る
- 成功条件：
  - 機能が仕様（spec）どおりに動く
  - 変更が小さく、レビュー可能で、ロールバックしやすい
  - テストとドキュメントが最低限揃っている

## 2. ドキュメントと言語
- 仕様書・計画・タスク・README・ADR（設計判断ログ）は **日本語**で書く
- コードの識別子（変数/関数/クラス/ファイル名）は **英語**（自然な英語）
- コメントは原則日本語（必要に応じて英語でも可）
- 生成物が英語に戻ったら、必ず日本語に直してから確定する

## 3. 進め方（仕様駆動の原則）
- 実装に入る前に、必ず以下を揃える：
  1) spec（何を/なぜ）  
  2) plan（どうやって）  
  3) tasks（分割された作業）  
- “動くけど仕様がない” 変更を増やさない
- 大きな変更は「最小の縦切り」で段階導入する（フラグや段階的移行を活用）

## 4. スコープと非目標
- スコープ：プロダクト価値に直結する機能／運用に必要な最小限の仕組み
- 非目標（やらないこと）：
  - 目的のないリファクタ（測定できる改善がない変更）
  - 過度な抽象化、先読みしすぎた拡張性
  - 使われていない最適化（早すぎる最適化）

## 5. 技術方針（ざっくり）
- 既存スタックを尊重し、変更は理由と移行計画を伴う
- 依存追加は「代替案」「メリット/デメリット」「運用コスト」を短く添える
- 互換性と再現性：
  - ローカルで再現できる手順を README / docs に残す
  - セットアップで詰まりやすい箇所はコマンド例を明記する

## 6. コード品質の最低ライン
- フォーマット・Lint は自動化し、手作業で整えない（CI で落とす）
- 変更は “読みやすさ” を最優先：
  - 1ファイルに責務を詰めすぎない
  - 命名（英語）で意図が伝わること
  - 例外/エラーは握りつぶさず、ユーザー/ログのどちらかに必ず出す
- リファクタは「先にテスト」または「同等性が確認できる安全策」を用意してから行う

## 7. テスト方針（最低ライン）
- 重要ロジックはユニットテスト（例：変換・バリデーション・ドメインロジック）
- 主要導線はE2E/結合のどちらかで守る（例：ログイン〜投稿〜閲覧）
- バグ修正は「再現テスト → 修正 → 回帰防止」を基本とする

## 8. セキュリティ / 機密情報
- 秘密情報（APIキー等）をリポジトリに絶対に入れない
- .env は例（.env.example）を用意し、実値はローカル/シークレット管理
- 認証・認可・データアクセスは “デフォルト拒否” を基本に考える
- ユーザー入力は必ずサーバー側でも検証する（クライアントだけに頼らない）

## 9. パフォーマンス / UX（最低ライン）
- 体感を悪化させる変更（重い処理、無駄な再レンダ、巨大バンドル）は避ける
- 画像・通信・DBアクセスはコストと速度の両面で意識する
- アクセシビリティは “最低限の破壊をしない”：
  - ボタン/リンクの役割を守る
  - フォーカス移動やキーボード操作を壊さない

## 10. 変更管理（PR/コミット/リリース）
- 1PR = 1目的（レビュー可能なサイズ）
- 破壊的変更は段階移行（互換 → 置き換え → 削除）
- マイグレーション/データ変更は必ずロールバックや影響範囲を書く

## 11. AI（Codex等）に関する作業合意
- AI は「提案と実装の補助」であり、最終責任は人間が持つ
- AI がやっていいこと：
  - 仕様→計画→タスクのドラフト作成
  - 既存コードに沿った実装、テスト追加、ドキュメント更新
- AI が勝手にやってはいけないこと（必ず明示確認）：
  - 大規模リファクタ／大量ファイルの置換
  - DBスキーマの破壊的変更、データ削除
  - 認証/課金/権限など高リスク領域の設計変更

## 12. Definition of Done（完了条件）
- 仕様に対して実装が揃い、動作確認ができている
- テストが追加/更新され、CI が通る
- README または docs に手順・注意点が追記されている
- 変更理由が追える（spec/plan/tasks の更新、または ADR）
